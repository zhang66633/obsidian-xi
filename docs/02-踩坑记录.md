# 踩坑记录

## 环境与工具链

### P1 raw.githubusercontent.com 在本机 DNS 解析到非公网 IP（2026）
- 现象：`web_fetch` 拉 GitHub raw 文件报 `resolves to a non-public IP address`
- 规避：改用 **GitHub MCP**（`mcp__github__get_file_contents`）读仓库文件，稳

### P2 firecrawl 匿名检索被拒 403（2026）
- 现象：`read_page` 内部 firecrawl 报 keyless 403，只能退化本地直取
- 规避：`read_page` 仍可用（本地引擎直取页面全文）；`firecrawl` CLI 搜索可用
  （已成功两次）。firecrawl 的 `search-feedback` 参数经 PowerShell 传 JSON 被剥引号，
  两次都报 invalid JSON——**后续要用就用 bash 风格 heredoc 或写成临时文件再传**

## 网关与 API

### P3 学校网关无 CORS 头 → 渲染层 fetch 不可用（2026）
- 现象：`Invoke-WebRequest` 探到 401 响应头无 `Access-Control-Allow-Origin`
- 结论：浏览器/fetch 路径必被 CORS 拦；Obsidian 插件内一律用 `requestUrl`
- 连带决策：v0.1 无流式输出（requestUrl 拿全量响应）

### P4 obsidian typings 1.13.1 > 注册表显示的本机 Obsidian 1.12.7（2026）
- 现象：`npm view obsidian version` = 1.13.1；注册表 DisplayVersion = 1.12.7
- **勘误**：窗口标题实测运行中的 Obsidian 是 **1.13.7**——注册表版本是过期的，
  以运行时为准；typings 用 1.13.1 对齐
- 规避：minAppVersion 设 1.12.7（保留下限兼容），API 只用稳定签名
  （已对照 1.13.1 的 d.ts 逐类核对）

### P5 grep 工具扫 `.dsh` 目录被 node_modules 断链炸掉（2026）
- 现象：`rg` 对断符号链目录报 error 3 刷屏
- 规避：grep 范围收敛到具体文件，或用 PowerShell `Select-String` 限定 `*.json`

### P6 typings 1.13.1 起 `Vault.cachedRead` 返回 Promise（2026）
- 现象：`tsc` 报 `Type 'Promise<string>' is not assignable to type 'string'`
- 结论：cachedRead 在新 typings 里是异步的；直接按同步 string 用会在新版上
  把全库读成空串（静默错库，比报错毒）
- 规避：VaultPort.readNote 整个改成异步（`Promise<string>`），
  Obsidian 实现直接 return 它的 Promise；旧版运行时同步返回，await 一下也安全

### P7 无效图标 id 让插件静默不加载（2026，哲的真机实测）
- 现象：插件文件放进 `.obsidian/plugins/lingxi/`、community-plugins.json 也登记了，
  Obsidian 重启后设置里没有面板、侧边栏不出现、**没有任何报错**
- 排查：Obsidian 的 obsidian.log 只有更新记录；直接解包本机
  `%APPDATA%\obsidian\obsidian-1.14.4.asar` 搜图标名——
  `message-star` 命中 **0 次**，`message-square` 命中 72 次
- 结论：`addRibbonIcon(iconId, …)` 收到不存在的 lucide id 会抛异常，
  onload 中断 → 整个插件被判加载失败。不是「图标缺失」是「插件挂掉」
- 规避：① 图标 id 一律先在目标版本 asar 里 grep 验证；
  ② 排插件「静默不加载」类问题的标准动作：解包 asar 核对 + 读 obsidian.log，
  不要只盯着自己的代码
- 附带发现：1.14.4 里 `community-plugins.json` 为 `[]` 时其他 3 个已装插件仍显示
  enabled——启用状态的存储位置疑似已变（未深究），写入 `["lingxi"]` 后
  lingxi 正常 enabled，未影响其他插件

### P8 真机安装路径（2026）
- 本地开发插件不能走社区商店；装法=三个文件（main.js / manifest.json / styles.css）
  拷进 `<vault>/.obsidian/plugins/lingxi/`，id 写进 `community-plugins.json`，
  重启 Obsidian。data.json 可预置（本次预置 `autoOpenSidebar:true` 实现启动即开面板）

### P9 obsidian-releases 的 PR API 对本机两个 token 均 404（2026）
- 现象：`gh api POST repos/obsidianmd/obsidian-releases/pulls` 与 MCP create_pull_request
  全部 404；**连 GET /pulls 读列表也 404**，而对 obsidianmd/obsidian-sample-plugin 的
  同样请求正常（返回 6 条）——排除 token 权限问题，是那个仓库的 PR 入口对 API 关闭
- 结论（2026-10-06 官方文档核实）：**PR 流程已废弃**。新流程见 P10。
  fork 上的条目提交（add-lingxi-plugin 分支）保留但不再需要，可放任自生自灭

### P10 社区商店提交流程 v2：网页目录，无 PR（2026，官方文档实测）
- 官方「Submit your plugin」文档（docs.obsidian.md/Plugins/Releasing/Submit+your+plugin，
  JS 渲染页，用 firecrawl scrape 抓的 markdown）现在的流程：
  1. GitHub 公开仓库（README + LICENSE + manifest.json）
  2. **GitHub release**，tag = manifest.json 的 version，附件 main.js / manifest.json / styles.css
  3. **community.obsidian.md** 登录 Obsidian 账号 → 绑定 GitHub → "Add your plugin"
  4. 自动审核反馈 → 改仓库 + 发新版本 release
- 目录读**默认分支 HEAD 的 manifest.json** 定版本；安装时按版本号去 release 拉文件
- 提交要求（同批抓取）需提前满足：无 fundingUrl 就不写、minAppVersion 取实测最低、
  描述 ≤250 字符英文句点结尾无 emoji、Node/Electron API 才需要 isDesktopOnly、
  命令 id 不带插件 id、样例代码清零
- 本项目据此整改：manifest 描述改纯英文句点结尾、minAppVersion 1.12.7→1.13.0
  （1.12.7 无实测，1.13.1 typings + 1.14.4 运行时才是验证基线）

### P11 PowerShell 5.1 的 Add-Content 默认 ANSI，会把 GBK 字节追加进 UTF-8 文件（2026-10-31）
- 现象：用 `Add-Content` 往 `styles.css` / 测试文件追加中文后，`read` 工具报
  `invalid UTF-8 text`；Vitest 测试名显示成乱码。
- 原因：本机 `pwsh` 实际是 Windows PowerShell **5.1**，`Add-Content` 默认按系统 ANSI
  （GBK）编码追加，而原文是 UTF-8。
- 规避：**优先用 `write`/`edit` 工具写文件**；必须用 PowerShell 时显式
  `-Encoding utf8`。已经混入的文件按「UTF-8 前缀 + GBK 尾部」分段解码后重写。
- 教训：编码问题不会让测试立刻红（测试名乱码也能跑绿），要主动用 `read` 工具复读。

### P12 package.json 与 manifest.json 版本号漂移（2026-10-31）
- 现象：manifest 0.4.2，package.json 仍 0.1.0；`npm version` 只改 package，旧脚本只管
  versions.json，manifest 要手改——三处各写各的。
- 规避：`version-bump.mjs` 改为同时写 manifest 与 versions；发布只走
  `npm version <x.y.z> --no-git-tag-version`，release workflow 再校验 tag == manifest.version。

### P13 用户 data.json 里 maxOutputTokens=90000（2026-10-31）
- 现象：本地库 data.json 的 `maxOutputTokens` 是 90000（默认 8192），旧 settings 合并
  完全不钳制数值；这样的值发给网关很容易 400。
- 规避：`mergeSettings` 对所有数值做区间钳制（输出 256–65536、输入 1000–200000），
  设置页用 number control 的 min/max 再做一道 UI 闸门。

### P14 声明式设置 API：`getSettingDefinitions()` 非空时 `display()` 根本不会被调用（2026-10-31）
- 依据：`obsidian.d.ts` 1.13.1 的 `display()` 注释明确写着
  “Not called when getSettingDefinitions returns a non-empty array”。
- 影响：不能「先写一半声明式再保留 display 兜底」——只要返回了非空数组，旧渲染就是死代码。
  因为 `minAppVersion` 已是 1.13.0，直接 Path A（删 display）是正确选择。
- 副作用：`control` 会绕过自定义 `saveSettings`，所以必须重写 `setControlValue` 做索引器同步。

### P15 用模长比给余弦剪枝是错的（2026-10-31）
- 错误假设：`|cos| <= min(||a||,||b||)/max(...)`，所以模长差太多可以跳过。
- 反例：`[0.01, 0]` 与 `[100, 0]` 模长比 0.0001，但余弦 = 1（同方向）。按模长剪枝会漏掉
  真正的重复笔记。
- 正确优化：只预计算模长避免每对开方；不剪枝。回归测试已固定该反例。

### P16 设置页改语言不生效（2026-10-31）
- 现象：设置里把 language 改成 en，只有 data.json 变了；界面、检索提示词都没变，
  要重启才生效。
- 根因：`saveSettings()` 只写盘，没有调用 `i18n.setLang` / 同步 `indexerConfig.contextPrefix`。
- 规避：所有设置变更统一走 `plugin.onSettingChanged(key)`；语言变更调用 `applyLanguage()`，
  同时刷新已打开的 ChatView。

### P17 本机 git push github.com:443 不通，gh API 通（2026-10-31）
- 现象：`git push` / `git ls-remote` 对 github.com:443 报 connection reset 或 21s 超时；
  同一时刻 `gh api` 访问 api.github.com 正常，仓库元数据也能更新；SSH 无公钥。
- 规避：用 GitHub **Git Data API** 重放本地提交（blobs → trees → commits → 更新 ref），
  再用 API 建 annotated tag。tag 的 push 事件仍会正常触发 GitHub Actions（实测 CI +
  Release 两个 workflow 都跑了）。
- 注意：API 重放出来的 commit SHA 与本地不同（树内容一致），因此本地 `git status`
  会显示 ahead；**不要**在恢复网络后直接 force push 覆盖远端。先 `git fetch` 对齐，
  或继续用 API 脚本追加提交。
- 另一个坑：PowerShell 的 `git show`/`readFileSync` 会把工作区的 CRLF 上传到远端，
  导致远端树比本地多两个字节（docs 末尾的 `\r\n`）；用「本地 index 内容（LF）→
  blob」重新提交一次即可，最终远端 tree SHA 与本地 HEAD tree 完全一致。

### P18 推理模型把思考写进 content，旧 JSON 提取拿到「示例 + 答案」拼盘（2026-10-31）
- 现象：整合页对比/缺口频繁显示「模型没有给出有效内容」，但把原文展开后能看到完整的
  `{"consensus":[...],...}` 就在末尾。
- 根因：qwen3.8-27b 先输出「我们需要输出 {"consensus":[...]} 这样的结构…」的思考，
  其中带 schema 示例；旧 `extractJsonObject` 取第一个 `{` 到最后一个 `}`，
  `JSON.parse` 必然失败。
- 修复：扫描所有 `{` 候选、字符串感知括号配对，取结束位置最靠后的合法对象；
  数组同样处理（`extractJsonArray`）；合并草稿从第一个 Markdown 标题开始截断；
  仍解析不了时 UI 展示原文并允许复制/保存。
- 验证：真实对比请求已能渲染共识/分歧/互补；合并草稿以 `# ` 标题开头；
  标签建议不会被思考里的示例数组抢答。
- 附带教训：不能只看「有没有 JSON」，要看 **哪一段** 才是答案；推理模型的
  `content` 不是「干净的结构化输出」，而是「思考 + 答案」的混合体。
